Scroll-edge blur renders under the content pane's toolbar, but not under the sidebar's traffic lights

Full API hierarchy and exact configuration for a native NSSplitViewController settings window, built to reproduce the question before posting it to the forums: why does NSSplitViewItemAccessoryViewController.preferredScrollEdgeEffectStyle work for a plain content split item but never render for a .sidebar-behavior split item, even though the safe-area math is identical between the two?

02 — Measured safe-area parity

The accessory is correctly wired on both sides

Captured via an internal diagnostics dump (window frame reads, safeAreaInsets, contentInsets) after opening the settings window:

contentViewController.view.safeAreaInsets = top: 54, left: 168scrollEdgeEffectAccessory.view.frame (window coords) = (168, 358, 420, 2)splitItem[0] (sidebar) .view.frame = (0, 0, 160, 396)  /* window is 412pt tall — 16pt shorter: the floating-card margin */splitItem[0] (sidebar) .view.safeAreaInsets = top: 46sidebarScrollEdgeEffectAccessory.view.frame (window coords) = (8, 358, 160, 2)sidebarScrollView.contentInsets = top: 46

8pt floating-card margin + 46pt safe-area = 54pt — exactly matching the content pane's 52pt toolbar height + 2pt accessory = 54pt. The accessory is correctly attached, correctly sized, and correctly contributing to the safe-area calculation on the sidebar side. Only the actual blur compositing fails to render.

03 — Experiment log

Three isolated on-device tests, ruling out configuration

04 — Relevant header doc comments

Quoted directly from the macOS 26.5 SDK

The split view item accessory's preferred effect for content scrolling behind it. To allow for a soft edge on the interior edge of a titlebar accessory:
splitViewItemAccessoryViewController.preferredScrollEdgeEffectStyle = NSScrollEdgeEffectStyle.softStyle; NSSplitViewItemAccessoryViewController.h
When YES, other items such as sidebars or inspectors may appear overlaid on top of this item's viewController and this item's safeAreaInsets will be adjusted with respect to overlaid content. Defaults to NO. NSSplitViewItem.h — automaticallyAdjustsSafeAreaInsets

Neither header, nor the WWDC25 session "Build an AppKit app with the new design" (session 310), documents any distinction in scroll-edge-effect behavior between .sidebar and .default-behavior split items — the feature is introduced generically as applying to "toolbar items, titlebar accessories, and split item accessories" alike.

05 — Official reference

WWDC25 session 310 — "Build an AppKit app with the new design"

developer.apple.com/videos/play/wwdc2025/310/ — the scroll-edge effect segment starts at 9:27; the split-item-accessory specifics are at 10:01.

For scrollable content, the scroll edge effect lives inside NSScrollView. The scroll view varies the size and shape of the effect based on the content floating above it. The effect adapts automatically as floating elements come and go. The scroll edge effect is applied automatically underneath toolbar items, titlebar accessories, and a new type of accessory, split item accessories. Split item accessories are very similar to titlebar accessories, except they only span one split within a split view controller, and they can be placed at either the top or bottom edge of the split. To add a split item accessory, create a NSSplitViewItemAccessoryViewController, and attach it to the split view item using the addTopAligned- or addBottomAlignedAccessoryViewController method. WWDC25 session 310, transcript at 10:01

Nothing in this passage — or the rest of the session — distinguishes .sidebar-behavior split items from .default ones. The wording ("a new type of accessory... they only span one split within a split view controller") reads as fully generic to any split, which is the basis for the question below.

06 — The question

Is the Tahoe scroll-edge-effect (NSSplitViewItemAccessoryViewController.preferredScrollEdgeEffectStyle) expected to work for a .sidebar-behavior NSSplitViewItem, or is this API currently scoped to non-sidebar split items only?

Every measurement above shows the sidebar receiving the exact same safe-area contribution as the content pane (54pt either way), and the identical accessory construction that produces a visible blur on the content side produces none on the sidebar side. Has anyone gotten the soft-edge blur to render for a .sidebar-behavior split item specifically — and if so, what differed from the setup above?

Regardless, how exactly does Apple implement the sidebar blur then? Regardless of the MacOS app you open, you'll see the sidebar tabs blurred as they are scrolled behind the Traffic Light buttons. MacOS Built-In apps that have this effect include:

  • Notes.app
  • Mail.app
  • Finder.app
  • System Settings.app
  • Music.app
  • Others I haven't explicitly mentioned here

My intent is to replicate very much the same effect they have done. If I've been able to successfully implement it on the content side (right of sidebar), then I'd expect it should also be possible on the sidebar side as well.
